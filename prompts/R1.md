## Epic R1-B — Schema Engine

### R1-B1 — Schema registry (migrations + models)

Depends: R1-A1. Read PLAN.md §2.2 (D9 architecture) and §3.
**Task (test-first):** migrations + Eloquent models for `workspaces`, `databases`,
`tables`, `fields` (type, position, options JSONB, validation JSONB), `views`,
`reports`, `templates`. ULID primary keys. Workspace scoping on every query
(single owner for now; membership table exists but only `owner` role — P30
groundwork). CRUD API endpoints for databases/tables/fields with Form Requests +
API Resources.
**AC:** Pest feature tests cover CRUD + scoping (user A cannot see user B's
database); `migrate:fresh` clean.

### R1-B2 — Field-type registry v1

Depends: R1-B1. Read PLAN.md §3 field catalog.
**Task:** a server-side **field-type registry** (one class per type implementing a
common interface: validate(value, options), normalize, serialize) for: short text
(max-length option), long/rich text, number (int/decimal/min/max), **date with
partial precision** (year-only, year-month, full, unknown — Eusèbe requires this),
boolean, select + multi-select, **reference** (target table, single/multi),
image/file (metadata only in v1 — upload pipeline is R1-C1), URL, email. GPS is R2 —
design the registry so adding it later touches no engine code (working agreement 4).
**AC:** unit tests per type incl. option edge cases; registry drives validation in
the record engine (next epic) via the interface only.

### R1-B3 — Schema versioning + destructive-change guard

Depends: R1-B2.
**Task:** additive schema changes (add field, rename label, reorder) apply freely.
Destructive changes (delete field, change type incompatibly) require an explicit
confirmation token from the client and produce a **data-impact preview** (how many
records carry values that would be orphaned/coerced). Orphaned values are
soft-retained (kept in the record JSONB under a tombstoned key) rather than erased.
Schema changes are recorded (who/when/what) for the activity log.
**AC:** feature tests: delete-field flow blocks without confirmation, previews
counts correctly, retains orphaned values, logs the change.

### R1-B4 — Property-based round-trip tests

Depends: R1-B2, R1-C1 (record storage).
**Task:** property-based tests (e.g. Pest + a generator helper): generate arbitrary
valid schemas from the field-type registry → generate arbitrary valid records →
store → read → serialize → assert lossless round-trip, incl. partial dates, accents
(é/È/œ), multi-values, max-length boundaries. Include a nasty-strings corpus.
**AC:** suite green over ≥ 1000 generated cases; failures shrink to minimal
reproduction; wired into CI.

## Epic R1-C — Record Engine

### R1-C1 — Record storage + CRUD + validation + files

Depends: R1-B2. Read PLAN.md D9.
**Task (test-first):** `records(id ULID, table_id, data JSONB, created/updated,
deleted_at, version)` per D9. CRUD API: create/read/update/soft-delete, validation
delegated to the field-type registry, unknown-field rejection. File/image upload
pipeline: content-addressed storage (Laravel filesystem), thumbnail generation,
attach to image/file fields as arrays.
**AC:** feature tests for CRUD/validation/upload; GIN index on `data`; soft-deleted
records excluded from lists.

### R1-C2 — Reference links + integrity (block + reassign)

Depends: R1-C1.
**Task:** maintain `record_links(from_record, field_id, to_record)` in sync with
reference-field values (transactional). Reverse-lookup endpoint ("records referencing
X" — powers "all works by this author"). Deleting a referenced record is **blocked**
with a structured error listing referencing counts; a **reassign** endpoint moves all
links from record A to record B (same table) then allows deletion — this is the
UI-reassign flow (P4).
**AC:** tests: link sync on create/update/delete; block error shape; reassign+delete;
reverse lookup paginated.

### R1-C3 — Query layer: search, filter, sort, collation, pagination

Depends: R1-C1 (links from C2 for reference filters).
**Task:** list endpoint per table with: full-text search across text fields
(Postgres tsvector, generated or side-table per D9); filters (field/operator/value —
design the query-param AST so R2's report builder reuses it); sort by any field with
**per-database locale/collation** (Postgres ICU collation — French accent ordering;
default `fr-CA` for the Literary Catalog); cursor pagination sized for TanStack
Virtual.
**AC:** tests incl. accent ordering (Éthier sorts with E), reference-field filtering,
search relevance smoke; p95 list latency measured on the R1-C5 fixture.

### R1-C4 — Activity log, history restore, trash, concurrency

Depends: R1-C1.
**Task:** per-record **activity log** (who/when/field-level diff) written on every
mutation incl. schema-driven ones (B3 retentions). Endpoints: record history,
**restore version** (creates a new version equal to an old one — edit-undo), **trash**
(list soft-deleted, restore, purge — purge respects C2 blocking). **Optimistic
concurrency:** updates carry the record `version`; stale writes get 409 + current
state (two-tabs case).
**AC:** tests for diff correctness, restore, trash restore/purge, 409 flow.

### R1-C5 — Scale fixture + performance targets

Depends: R1-C3.
**Task:** seeder generating a synthetic database at target scale (PLAN.md: 100k
records, 50-field table, realistic value distributions, links, images metadata).
Benchmark script (repeatable, documented) measuring: list p95 (< 200 ms), search
p95, single-record read, reference reverse-lookup. Findings + any index tuning as a
report in `docs/PERFORMANCE.md`. CI job (manual trigger) runs a reduced version.
**AC:** targets met or deviations reported with tuning recommendations before R1-D
list views build on top.

### R1-D2 — Form/structure builder

### R1-D5 — List & detail views

### R1-D6 — Design system: Tabler base, Maxton-inspired green theme (D5 ✅)

Depends: R1-A2; ideally lands **early** so D1–D5 build on the themed shell.
**Context:** D5 is ratified — code base = **Tabler** (MIT, Bootstrap 5,
https://github.com/tabler/tabler) + Tabler Icons, fully AGPL-compatible. The visual
*direction* is inspired by the Maxton admin template's horizontal-menu blue-theme,
which the user holds under **Envato Elements** — therefore Maxton is a
**reference-only** artifact on the user's machine: ⚠️ **no Maxton file, SCSS,
markup, or image may ever enter the repo.** Ideas yes, files never. What we take
as inspiration: horizontal menu layout, a deep-dark theme with popping accents and
strong contrast (Maxton's blue-theme uses ~`#0f1535` body / `#070c29` cards /
`#0d6efd` accents — study the *relationships*, re-express them natively in Tabler).
**Task:**
1. Integrate Tabler SCSS into the Vite build as `packages/theme` (isolated,
   swappable); adopt Tabler's **horizontal navbar layout**; wire theme switching
   to the P21 toggle.
2. **Green dark theme (the signature look):** build with Tabler's CSS
   variables/SCCS maps a dark theme whose hue family is green — v2's `#459e00` as
   primary, `#67b021` for hovers, deep green-tinted dark backgrounds mirroring the
   depth/contrast relationships of Maxton's navy theme (equivalent lightness roles:
   body vs card vs elevated surfaces). Provide light + dark + green-dark modes.
   Verify WCAG contrast. Present a themed screen to the user for sign-off before
   rolling out.
3. React layout components on Tabler markup (navbar, breadcrumbs, cards, page
   shells) — no jQuery anywhere; tables via TanStack Table styled to Tabler;
   charts later via ApexCharts-react.
4. Component inventory: map each upcoming UI need (D2–D5 builders, forms, lists,
   auth screens) to Tabler components/pages; note where custom work is needed
   (the three visual builders); document in `docs/DESIGN-SYSTEM.md`.
5. Heritage nod (P23): the v2 green is the theme itself; remaining question is
   FontleroyBrown as display font for headings/brand (pending the R0-S8
   font-license conclusion) — propose, user picks.
6. A11y pass on the themed shell (labels, focus, contrast, keyboard) + empty states.
**AC:** shell + one full CRUD screen themed in all three modes; `packages/theme`
contains only Tabler-derived/original code (PR checklist item); DESIGN-SYSTEM.md
merged; axe/a11y smoke clean; no jQuery in the bundle.

## Epic R1-E — Templates & Import

Depends: R1-B3.

views/layouts, reports placeholder) without data. Export any database as a template;

a documented upgrade-path policy (installing v2 over an existing v1-derived database
proposes additive diffs only). Demo-dataset variant: template + sample records.
**AC:** round-trip test (export → install → export → identical); format spec in
`docs/TEMPLATE-FORMAT.md`.

### R1-E2 — CSV import wizard

Depends: R1-C1; UI in client.
**Task:** CSV upload → parsing (encoding detection incl. latin1, delimiter sniffing)
→ column-to-field mapping UI (create missing fields inline, typed) → **dry-run

target records by a chosen display field.
**AC:** Playwright: import a fixture CSV incl. accents + a bad row; dry-run shows the
bad row; import succeeds with 1 rejection listed; feature tests for coercion matrix.

### R1-E3 — Literary Catalog template + demo datasets

Depends: R1-E1; field types from R1-B2. Read PLAN.md §2.2–2.3 (this template must be
able to represent all of it).
**Task:** build the **Literary Catalog** template: tables Works, Authors, Periodicals,
Publishers, Printers, Locations, Genres, Categories, Frequencies — fields mirroring
PLAN.md §2.2 (partial-date fields for author birth/death and publication year+month;
140-char short description; multi-image; reference fields wired; notes). Views and
card layouts approximating v2's browse dimensions (by title/author/year/genre/
category). Stretch (schedule permitting): Issues (Numéros) + Articles + Illustrations
tables per P6. Also one small unrelated demo template (e.g. "Recipe Box") + demo
dataset to prove genericity.
**AC:** template installs cleanly; a hand-entered sample work flows through form →
list → detail; demo dataset installs.

### R1-E4 — Eusèbe importer

Depends: R1-E3, R1-C1/C2; goldens from R0-S3 for verification.
**Task:** `php artisan archive:import {path}` (path = `EUSEBE_DUMP_PATH`; the dump
never enters the repo): parse the MySQL dump (or import via a throwaway MySQL
container and read from it — implementer's choice, document it), map v2 tables/
columns to the Literary Catalog template per a `docs/SCHEMA-MAP.md` you write;
cleaning rules: `0000-00-00` → partial-date-unknown, `~`-split images → arrays

**AC:** counts match PLAN.md §2.2 exactly; SQL-level spot-check vs R0-S3 goldens
(e.g. title lists for 3 authors, annex year grouping) matches; report committed
(sanitized — no personal data beyond what the public goldens already hold).
