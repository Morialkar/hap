Read `~/Literary-Heritage-Archive/PLAN.md` (D8, §3.2, §5 R3) and
`docs/CONVENTIONS.md`. Decision D8: Tauri 2 shells around the existing React client;

## R3-A — Tauri 2 feasibility spike (FIRST, timeboxed)

**Context:** this spike gates the whole release. Timebox: 1 week. Its output is a
**go/no-go report**, not production code.

**Task:** wrap `apps/client` in Tauri 2 and prove, on macOS + Windows (desktop) and
**real iPhone + Android hardware** (mobile):
1. SQLite via the Tauri SQL plugin: create/read/write a database file; measure a
   10k-record query.
2. Filesystem: write/update a folder of Markdown files (vault dry-run) in a
   user-chosen location; mobile equivalents (app documents dir; export/share sheet).
3. MapLibre GL rendering in the webview + loading a local PMTiles file (offline
   maps).
4. Build/packaging pipeline sanity: dev loop time, binary sizes, signing
   requirements inventory (Apple dev account etc.).

**AC:** written report per platform with pass/fail per capability + performance
numbers; explicit **go/no-go recommendation**; if no-go: the same 4 checks run
against the Capacitor+Electron fallback and D8 updated in PLAN.md with user
ratification.

## R3-B — Local data driver + offline mode

Depends: R3-A go.
**Task (split first, then build):**
1. SQLite mirror schema (records as JSON per D9: JSON1 + R*Tree for GPS; links
   table; FTS5 for offline full-text search — feature parity with R1-C3 search).
2. Implement the `packages/core` repository interface's **local driver**; the app
   picks remote (web/signed-in) vs local (desktop/mobile default) transparently —
   **local mode requires no auth and no network, ever** (D7 amendment).
3. Offline mutation queue (for the future sync in R4): every local write also
   records an oplog entry with HLC timestamp (design per D12 now, sync later).
4. All R1 features must pass locally: run the relevant Playwright suites against
   the desktop build (webdriver) as the acceptance bar; document exclusions.

**AC:** app works in airplane mode end-to-end (create database from template, add
records with images, search, browse); R1 journey suite green against the local
driver; oplog schema reviewed against D12.

## R3-C — Human-readable vault

Depends: R3-B.
**Context:** PLAN.md working agreement 5 — the vault is a **contract**: versioned
format spec, round-trip tested. Purpose: if the app vanishes, a person can still
read their archive.

**Task (split first, then build):**
1. Vault format spec (`docs/VAULT-FORMAT.md`, versioned): per database — `schema.json`
   (template-format reuse from R1-E1), one folder per table, one Markdown file per
   record (YAML frontmatter = field values incl. locality snapshots; body = long-text
   fields), `files/` for images (content-addressed names + human-friendly links from
   the MD), and a generated human `README.md` explaining the layout.
2. Continuous export: vault (plus a SQLite file copy) written to a configurable
   folder on every change (debounced) on desktop; on-demand export on mobile +
   web download (zip).
3. **Re-import:** vault → platform database, lossless. This is the round-trip
   guarantee (export → import → identical records) and it doubles as
   disaster-recovery restore.

**AC:** round-trip property test (incl. accents, partial dates, images, GPS);
vault of the imported Eusèbe database manually reviewed for human readability
(the user reads it); format spec versioned.

## R3-D — Packaging & distribution

Depends: R3-B (app works locally); R3-C recommended.
**Task (split first, then build):** installers + code signing for macOS/Windows/
Linux; Tauri auto-updater with signed releases; iOS/Android store-readiness
inventory (assets, privacy declarations — note: account deletion req. only applies
once accounts exist in R4; local-only app has no accounts); offline map bundle
(PMTiles region download manager — which regions ship by default is a user
decision); CI release pipeline (tag → build matrix → signed artifacts).

**AC:** a tagged release produces installable, signed builds for all desktop
platforms + sideloadable mobile builds; auto-update tested desktop-to-desktop;
store submission checklist written (submission itself waits for user).
